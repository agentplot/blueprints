Capture Pipeline

headwater, eddy and the folder drop notice things and print captures. millpond keeps them as an inbox of signals. A Claude session curates the inbox in batches you accept, joining signals into items, and each item goes to one worktree or into crew's plan. sluice lands the work.

The contract

An adapter writes JSON Lines to standard output. Each line holds one capture, the cursor to hand back next run, or done with the run's counts and failures. millpond runs it as <command> --raw-dir <dir> [--cursor <c>], and Flywheel later runs it the same way.

{"capture": {"key": "release/mise/2026.10.10", "source": "release",
  "event_at": "2026-10-10T14:02:11Z", "title": "mise 2026.10.10",
  "raw": ["mise-2026.10.10/notes.md", "mise-2026.10.10/release.json"],
  "excerpt": {"text": "…the notes, whole…", "kind": "ask",
    "asserted_by": "jdx/mise",
    "assertion": "mise 2026.10.10 is released; the repository pins 2026.9.18.",
    "subjects": ["release", "mise"], "argues_with": ["packages/mise/default.nix"]}}}
{"cursor": "2026-10-17T04:30:05Z"}
{"done": {"listed": 14, "failed": [{"what": "github:jdx/mise", "why": "HTTP 502"}]}}

The lines (standard output)

  • Small: what millpond checks and what enters git as the capture and its signal.
  • Read by millpond alone.

The raw files (--raw-dir)

  • The material whole, as the source served it: a transcript, the full notes, a log. It never enters git.
  • Banked by millpond, then read by a reader session, by the verbatim check, and by a person following the pointer.

millpond land is the intake: it takes lines from whoever pipes them. millpond run <part> starts an adapter with a fresh raw directory and its last cursor, lands what it prints, and keeps the cursor and the run's status. millpond tick runs every part whose schedule is due, so one timer serves a host.

A meeting's capture is the same shape with no excerpt, so millpond marks it unread and a reader takes it. The key is the event's identity everywhere: release/<name>/<version>, meeting/wispr/<id>, folder/<folder>/<sha256>.

The inbox and curation

The inbox

  • A git repository, or a branch in one, holding captures, signals, moves and items in Flywheel's record formats.
  • millpond.toml at its root names its parts, each with a schedule and the one host whose tick runs it, its cut, its reader and where items go.
  • On its own: a repository of yours. With crew: the partition's flywheel branch. With Flywheel: the same files, no import.
  • crew's folders and the meeting corpus come in once through millpond's import, keeping their keys.

millpond's tools, over MCP

  • signals lists by state, source, age, capture or subject.
  • capture reads a capture and its raw material.
  • read writes a capture's signals, refusing an excerpt not found verbatim.
  • moves writes a batch in one commit; items lists items.
  • brief writes an item's brief; send sends it to a worktree.
MoveConsequence
dropRecords the reason.
answeredNames the claim or record that settled it.
challengeWeighs against a claim; only an inbox beside Flywheel's claims has one.
joinMakes an item, or grows a proposed one, from any number of signals.
attachPuts the signal on an item already sent.
routeOffers a chore, which millpond makes an item of one, or an ask, which it records.

A backlog of hundreds goes fifty at a time: the curate skill asks for the oldest unmoved, reads the raw material of the unclear ones, and proposes, for example, drop eighteen, answer six, join twenty-six into five items. You accept or change rows, and one moves call writes the batch. herdr's pane shows the counts, opens a batch row by row, and sends an item with one key. An inbox crew keeps hands its items to crew's planner and sends none to a worktree.

Three sources

Releases: headwater

  • A tool for dependencies, never a capture framework. It asks deps.dev, GitHub, ecosyste.ms, each registry and OSV.
  • headwater capture prints a capture for every release newer than its pin, and millpond's dedupe lands each once. Each release is its own excerpt.
  • A watch-list entry keeps today's key, release/<name>/<version>, so nothing swancloud already landed lands again.
  • In a repository crew runs, the herdr fix key hands the release to millpond, since a bump comes only as a chore.

Meetings: eddy

  • A program lists meetings and a session reads them. The wispr part is an MCP client with its own sign-in.
  • One part per service: wispr first, webex and teams when a partition needs them, sharing the key, the details and the raw layout.
  • Others publish meeting plugins of their own; a part counts when it passes the meeting checks.

Any other file: the folder drop

  • Flywheel's folder adapter, built into millpond: millpond capture folder <dir>.
  • Keyed by the file's sha256, so a file dropped twice is one capture.
  • No excerpt: a reader tells a transcript from an email by what it holds.
  • An adapter with a generic source ships in millpond; one wrapping another tool's domain ships with that tool.

Ten decisions to rule

  1. headwater is for dependencies and eddy for meetings. The work every source shares is millpond's, through the contract.
  2. millpond is a standalone tool, the inbox: it runs adapters, keeps captures and signals, serves the tools curation works through, and sends an item to a worktree. crew calls its command line as it calls sluice's.
  3. Flywheel's statement owns the contract and the record formats. flywheel-next's crates implement them once; millpond is built on them, and Flywheel's host later on the same crates.
  4. An inbox is a git repository, or a branch in one, in Flywheel's formats. crew's partition branches become inboxes, crew's folders and the meeting corpus are imported once, and Flywheel reads the same inboxes with no import.
  5. The unit of work is an item, the signals curation joined, one or many. millpond sends one item to one worktree; planning across items is crew's planner today and Flywheel's later.
  6. A Claude session works a backlog through millpond's tools, proposing moves in batches you accept or change. herdr shows the counts, reviews a batch and sends an item.
  7. A program lists meetings and a session reads them. eddy holds a part per meeting service, its Wispr part an MCP client that starts no Claude session. Others publish meeting plugins of their own.
  8. An adapter whose source needs no other tool ships inside millpond. One that wraps another tool's domain ships with that tool, so headwater's and eddy's parts stay theirs.
  9. "Plugin" replaces Flywheel's "package" and "bundle".
  10. The release adapter lands through millpond on trial before headwater exists, so the contract carries live captures first.

Each phase ends with something running on real work. Once millpond's core exists, headwater, eddy, millpond's plugins and crew's move onto millpond proceed side by side.
