The loop layer

The design center for the flywheel's loop layer. Seven tabs: why the layer exists, the vocabulary it runs on, every flow written down as a state machine, where the human is, how it spans hosts, the machinery as it is on disk, and the decision ledger.

Why

What this layer is for

the model before the mechanism

A few developers — today, one — a fleet of agents, and ideas arriving faster than they can be built: a sentence in the car, a meeting transcript, a bug report, a complaint about a flag name. The loop layer is the factory discipline that turns that stream into shipped code: every fragment is routed the day it arrives, uncertainty is burned into records before anything is built on top of it, and the operator's attention is spent at a handful of named moments instead of continuously.

Three commitments everything else derives from these

1 · Everything is a file in a change. An actor holds no state its change directory does not. Questions, decisions, assertions, tasks, proposals, even parked messages are files on git — so any actor can die at any moment and a fresh one resumes by reading. Actors are disposable; the record is not. This is what makes the hosts tab cheap.
2 · The inner loop never writes the outer. Design (intents) and construction (bolts) corrupt each other when interleaved. A construction finding travels back as a proposal or a question — never as an edit to a design record. Building something because an agent asked would let the outer loop be written by the inner one.
3 · Attention is batched. One approval per release batch, never one per item. One annotation round per page. One Discord sentence per routing question, non-blocking. If a moment isn't in the human-loop enumeration, no agent waits on the operator there.

The system, as one conveyor

Raw input enters at dispatch. The design loop converts uncertainty into decisions and accretes direction as assertions. When a coherent batch of assertions is settled, its owner releases it — the one gate — and it becomes a bolt, whose loop drives proposals to main. Findings flow back the other way, routed by kind. Both loops write their own records; the books and the map receive the destination from the design loop only.

Six actors who runs, and what they own

An actor is a running Claude session, not a persona. Three things define one: a herdr name (how anything addresses it — herdr agent prompt intent-flywheel), an agent profile (.claude/agents/<name>.md — frontmatter of name · description · tools · model, and a body that becomes the session's system prompt, loaded by claude --agent <name> before the first prompt so the role survives compaction), and one change it owns. Note what is absent: none of the three names a host — which is the whole hosts story.

A persona is a different object entirely — .claude/agents/user-*.md, a stand-in for someone who uses the built thing (a data scientist at a CLI, a DevOps engineer deploying it). A persona never owns a change; it is a lens a review session runs under. Same directory, opposite job — which is why the user- prefix is load-bearing.

One question assigns the profile: does the session build a lavish page, is it design without one, or is it construction? The profile carries the loop; the skill carries the type.
The set is a floor, not a ceiling — two open edges. Dynamic workflows may want further actor kinds beyond these six — personas first, possibly others — running visibly under the same rules, which is part of what the rule-1 question decides. And dispatch may need session types of its own — a release-definition session at handoff time, rather than staying a pure router that never works a batch. Both are in the open ledger (→ Decisions).

Thirteen session types one set across both loops

Three envelopes what an agent may send

kindbodywhat the receiver does
respondanswer (≤3 sentences) · evidence[] · statemoves the item along its ladder
extend-boltproposal · repo · claim · review · sourcea bolt conductor writes a new proposal file; the bolt grows
extend-intentrecord · type · question · turns-on-it · sourcean intent conductor writes a question or assertion record
One header on all three: to · from · re · kind, where re is a change-relative path — the filesystem is the id space, so a reference either resolves or it does not. Sending closes nothing: the sender keeps the item on its own list until it observes the receiver carrying it. Two transports, one block: herdr agent prompt when the target runs, a file in its inbox/ when it does not — paste-identical, or they drift apart.
Who gets an envelope — the direct-vs-dispatch rule. Agent-to-agent traffic travels direct: the sender names the owning change (re: is a change-relative path) and uses prompt or inbox — a persona finding goes straight to its bolt conductor, an extend-intent straight to the owning intent conductor. Dispatch enters the path only when a human is at either end — raw input inbound from a developer, a relayed question outbound to one — or when the sender cannot name the target change, which is what routing means. This is the rule that reconciles the two records that looked at odds: the envelopes define the agent legs, the bridged singleton defines the human legs.

Who writes what the write matrix — every flow honours it

The one serialization point: the conductor is sole writer on main. A session closes what its work order assigned; the conductor opens what the session discovered — new tasks, new questions, re-sequencing — because a session sees its batch and never the whole queue.
And one owning developer per change. "The operator" in this page is a role resolved per change, not one person: every intent and every bolt names the human whose word settles its decisions and whose approval is its gate. Today one developer owns everything — the design treats that as the N=1 case, with zero added ceremony — and the two loops scale by different people: intents by designer, bolts by builder (→ Hosts & owners).
Flows

Every work item, written down

deterministic on paper, judged in the running

The system will not work right until every piece of work that flows through it has an exact, written-down state machine. These are written deterministically so the skills, schemas and envelopes can be designed against them — not so agents execute them as scripts. Each machine names the states, who moves an item between them, and by what mechanism. Where a step was genuinely open, a card sat beside it — all are now settled, shown in place as green notes. Legend: operator dispatch intent conductor bolt conductor session — amber states are where a human appears; green states are terminal.

The ten state machines

1 · Raw input an idea, a transcript, a bug report, a complaint

The only object that exists outside a change. It lives on dispatch's own list until every routing is observed carried.

hearddispatch reads it once→ routedone input, N routings→ carriedreceiver visibly holds it→ observed
transitionmoved bymechanism
heard → routeddispatchreads the input once and decides its routings — a single input may fan out to several (see walk 1). If the routing is ambiguous, one non-blocking Discord question to the operator.
routed → carrieddispatchper routing: create a new intent change (its one scaffold write) · extend-intent / extend-bolt envelope by prompt or inbox · stand up a bolt-quick for a tracked chore
carried → observeddispatchsending closes nothing — dispatch keeps the item until the receiver's records visibly carry it (the question file exists, the proposal file exists), then forgets it

2 · Open question questions/<slug>.md

One uncertainty, burned down to a decision. Two paths close it: a session produces the answer, or the operator already has it.

transitionmoved bymechanism
(anything) → raisedintent conductorwrites questions/<slug>.md with State: open, what turns on it, what is already known — from a session report, a drained envelope, or dispatch's relay

shortcut: raised → closedoperator via conductorwhen the operator answers directly (a Discord sentence, an annotation), the conductor records the decision itself — no session is spawned to file an answer that already exists
closed → propagatedintent conductorthe assertion sweep: the conductor walks the whole assertion set against the decision — every assertion the answer touches is revised, and "none moved" is recorded in the merge commit, so silence is a statement rather than an omission. Then the writeback task if a chapter moves, and dependent tasks unblock.

3 · Decision decisions/<slug>.md

needed→ draftedoperator's word, or work-order latitude→ settled→ recordedwriteback · assertions · tasks→ propagated
who settleswhen
operator — the change's owneranything their word created, anything a work order marks as theirs, every release. Their word is quoted in the record's Context.
sessionwithin its work order's latitude — the order names the questions it may close. Overturning the operator's word is never in latitude; it escalates instead.

A decision is append-only in effect: it is rewritten when next edited for another reason, never annotated with its own history. Reversing one is a new decision that names what it replaces.

4 · Assertion assertions/<slug>.md — the mineable unit

A claim about what should become true in a repo. It accumulates in the intent, is released in a batch, mined into proposals, and closes only on evidence from main.

raisedrevised as direction moves→ opengrouped into a release batch→ releasedbolt conductor mines it→ minedverified on main→ closed
transitionmoved bymechanism
raised → openintent conductorfiles the claim with Repo:, State: open, the why, and boundaries — from operator feedback, review findings, session reports, drained envelopes
open → open (revised)intent conductorthe drain rule: an envelope touching an assertion revises it and re-walks downstream records in the same commit. The operator does not review these edits as they happen — see the timing note below.
open → releasedoperatorthe handoff approval — one approval for the whole batch, the only gate there is
released → minedbolt conductorturns the claim into one or more proposal files in its registry; the assertion records which bolt carries it
mined → closedintent conductorflips State: with evidence cited — a commit on main, a verified file, never a confirmation relayed secondhand (a confirmation is not evidence when the confirmer verified a neighbour)
When does the operator see an assertion? Not at write time. Assertions move daily as inputs arrive; reviewing each edit would be one-approval-per-item by another name. The operator reads them at the moments that already exist: a design session's page (where coupled assertions are options to choose among), and the handoff request (where the batch is listed in full). Between those, correcting one is an ordinary raw input: a sentence to dispatch.

Nine walks the permutations, each as one event end to end

Each walk is one concrete event traced through the machines above. Together they cover the interactions the machines alone leave nebulous — who acts, in what order, and where the human is.

Walk 1 — a meeting transcript arrives, and fans out five ways

Settled — the envelope carries the excerpt. Dispatch never writes inside an existing change. Transcript material travels inside the extend-intent envelope; the conductor files it under its own sessions/ and mines it.

Walk 2 — "turn the loop": what the morning start actually runs

  1. operator says go — a Discord message to dispatch, or just opening the herdr board.
  2. dispatch drains its own queue first: parked answers relayed to their askers, queued routings prompted to conductors now running.
  3. each intent conductor starts its turn: drains its inbox (revise earliest artifact, re-walk forward, delete in the same commit) — so the board reflects overnight arrivals before any new work is chosen.
  4. each intent conductor runs its loop: query pending tasks → an agent returns what can start, batched with a session type each → sessions launch in their own worktrees → merge as each finishes → re-query.
  5. each bolt conductor does exactly the same against its proposals and tasks — same shape, different depth.
  6. sessions that need the operator surface on the cheapest channel that carries the answer; nothing else stops — a blocked batch idles while its siblings run.
  7. The loop goes quiet when nothing is startable and every open question waits on the operator or on a running session. Quiet is a state, not a failure.

Walk 3 — an open question, end to end

  1. Walk 1's routing 2 landed: intent-atlas-auth drained the envelope and filed questions/zuplo-header-forwarding.md, State: open.
  2. the conductor appends under the research section of tasks.md: "measure how zuplo forwards auth headers — closes questions/zuplo-header-forwarding".
  3. Next loop pass: the analyse agent groups it with a neighbouring measurement into one research batch.
  4. a research session gets its work order — change id, the two task lines, session dir, worktree sess/zuplo-headers, the research skill — and measures rather than remembers.
  5. the session writes decisions/zuplo-forwards-verbatim.md, flips the question to State: closed → decisions/…, checks its two lines — all in its worktree — and reports.
  6. the conductor merges the branch. On main, it propagates: appends the writeback task for the chapter the answer moves, revises the one assertion that assumed the opposite.
  7. Had the operator answered in step 1's morning triage instead — one sentence on Discord — steps 2 through 5 never happen: the conductor records the decision directly. A session exists to produce an answer, not to file one.

Walk 4 — a design session completes: where the results actually go

  1. the session ends its final annotation round. Its outputs are in exactly three places, and each has one owner.
  2. Its session directory — the page, the report, the measurements. Its own write, kept forever, never rewritten once the session closes.
  3. The records its work order named — decision records for the questions it closed, the State: flips, its own task lines. Its own writes, made in its worktree, admitted by the merge.
  4. Everything it discovered but was not assigned — new questions, follow-on work, a defect in a sibling record — travels up in its report envelope. The conductor opens those on main, because the session sees its batch and never the whole queue.
  5. the conductor runs the assertion sweep — the report envelope carries everything the session closed and found, and the conductor walks the assertion set against it: revising the touched, opening the missing, recording "none moved" when that is the truth. A design session's learning that never lands in an assertion is learning the release will not carry — the sweep is what makes decision records feed the handoff instead of resting in the ledger.
  6. the conductor merges, then updates intent.md only if direction moved — the destination paragraph changed, the scope changed. Task progress never touches intent.md; that is what tasks.md is for.

Walk 5 — assertions stack up, then release as one batch

  1. Over a week, intent-atlas-auth accretes six open assertions from transcripts, closed questions, and review findings. None was individually approved — see machine 4's timing note.
  2. the conductor judges four of the six form a coherent delivery (one repo, one seamless story) whose questions are all closed. It opens a Handoff task naming the four, the repo, and the proposed member: bolt-default.
  3. a handoff session composes the request: the four assertions in full, the depth argument, what stays behind and why.
  4. operator — the intent's owner — approves — the release. One approval, four assertions, and this is the moment they read the set whole; they name the bolt's owner in the same word. They may pull one assertion out; the batch shrinks and releases without it.
  5. dispatch stands up bolt-atlas-auth binding bolt-default; a bolt conductor owns it from its first prompt and mines the four assertions into proposal files.
  6. The two assertions left behind keep accumulating — the next release batch, or folded into a live bolt later by extend-bolt if its scope covers them. Work stacks in the intent; a bolt is never created per assertion.

Walk 6 — a writeback, from settled to on the page

  1. the conductor records a decision that moves a chapter, and appends a writeback task naming the chapter in the same turn.
  2. The task waits until its deciding question set is closed — writing the destination from a moving answer is the one thing writeback never does.
  3. The analyse step batches it with sibling chapters of the same book: one book, one worktree, one gate run.
  4. a writeback session rewrites the chapters whole, in destination voice, moves the map, runs the three gates, checks its lines, reports.
  5. the conductor merges. The chapter is now the latest-and-best; the decision record stays as the why.

Walk 8 — a mid-flight correction to a live bolt

  1. operator, in the car: "the flag should be --scope, not --realm." One sentence to dispatch.
  2. dispatch routes it: the flag lives in bolt-atlas-gateway's registry → extend-bolt envelope, prompted (the conductor is running).
  3. the bolt conductor drains it under the standard rule: revise the earliest artifact touched. The proposal file's claim changes; the proposal was already specced, so it regresses to to-spec and the spec is re-run. Downstream states are re-earned, not kept.
  4. No human beyond step 1: the correction is the operator's own word, and the drain rule makes its consequences mechanical.

Walk 9 — a chore that belongs to no intent

  1. operator: "rename the CI job in cortex-kit, it collides with the new one."

  4. Either way a bolt conductor owns it — every released piece of work has an owner to catch feedback and a place for it to land. Nothing lands on a bare branch off main.

Parking — conductors do not stay resident

An idle conductor is parked, not left running. Idle is observable — nothing startable, every open question waiting on a person or a running session — and parking loses nothing: a conductor's entire state is its change directory on git, and the two-transport rule already covers absence, so envelopes fall back to inbox files the moment the pane is gone. flywheel park <name> stops the pane and marks the manifest row parked; the per-host waker (or the owner) revives it when its inbox goes non-empty. Intent conductors park often — design arrives in bursts. A bolt conductor parks between its last merge and late feedback. Hosts & owners

Scaling past one machine — and one person

new design space — nothing here is settled

Two scaling axes, deliberately separate. Machines: the office workstation and an EC2 fleet, dispatch somewhere central, bolt conductors wherever compute is cheap — and a machine can restart and have one command put its actors back. People: more than one developer, where one may own every intent while several own bolts, because the two loops scale by different roles. Machines first, then owners.

The one genuinely new problem: the two-transport rule keys on whether the target is running, and across hosts that generalizes to whether it is reachable. Cross-host design is exactly two things: making prompt-reachability true across machines, and making sure a parked envelope gets noticed — because "drained at the owner's next turn" assumes an owner that has turns, and a conductor on a rebooted host has none until something starts it.

The topology, drawn

Owners — scaling past one person

Machines were the easy half: actors were host-agnostic before they needed to be. People need one new fact and three rules. The fact: every change names one owning developer — the human whose word settles its decisions and whose approval is its gate. Today one developer owns everything; that is the N=1 case and must cost nothing extra. The rules:

Intents scale by designer, bolts by builder — independently. One developer can own all intents while several own bolts, which is where the leverage is: the automation bar means a bolt owner mostly answers andon pulls and review: human rounds, so one builder can own many bolts — and many builders can own many more. The two axes never have to move together.
The release is the transfer of responsibility. The intent's owner approves the batch and names the bolt's owner — themselves by default, another developer to scale out. From that word on, construction questions resolve to the bolt's owner, and extend-intent findings still go home to the intent's owner. A bolt owner never fields design questions; an intent owner never fields andon pulls on work they handed off.
Ownership is design state; placement is runtime state. Who decides must survive any pane move, so it lives on the change — owner: in its .openspec.yaml (decision 22) — and is archived with it. Which host runs the pane changes when machines do, so it lives in the manifest (decision 29, scoped to exactly this). The manifest derives intent-conductor placement from ownership; it never defines ownership.

One release with two owners, walked

  1. you own intent-atlas-auth; its conductor runs at your workstation. You approve the four-assertion batch and name Dana as the bolt's owner — that naming is part of the release, not a separate step.
  2. bolt-atlas-auth is stood up on the fleet binding bolt-default, owner: Dana. Dana's machine is irrelevant — a bolt conductor needs compute, not its owner's browser.
  3. A test session finds the deploy contradicts the intent → new proposal file, the bolt grows. No human — unchanged from walk 7; ownership adds nothing to the automatic path.
  4. A persona asks a question the intent never covered → extend-intent → the question record lands in your intent, and its answer follows the design loop's channels to you. Dana never sees it.
  5. A build agent pulls the andon cord → dispatch resolves re: → the bolt change → owner: Dana → DMs Dana's Discord. The line holds until Dana answers.
  6. Dana's conductor merges to main; your conductor verifies the assertions closed with evidence. Two humans, zero meetings, and each was interrupted only for what they own.
Dispatch stays one pane for the whole team. One bot token binds one session — that constraint doesn't move — and the allowlist already admits multiple senders. Inbound is symmetric: any developer DMs the same bot, and their message routes under their name as from:. That shared shape is settled (decision 23): one team dispatch, owner routing.

// authored in the moment, passed inline to Workflow()
export const meta = {
  name: 'bolt-default',
  description: 'Query tasks, analyse dependencies, batch into sessions, merge, re-query.',
  phases: [ {title:'Query'}, {title:'Analyse'}, {title:'Work'}, {title:'Merge'} ],
}

while (true) {
  phase('Query')
  const pending = await agent(`openspec instructions apply --change ${args.change}
     --json — return every task with done == false`, { schema: PENDING })
  if (!pending.tasks.length) break

  phase('Analyse')
  const plan = await agent(`which of these can start now? group them into batches
     one session could take, each with its session type`, { schema: BATCHES })

  phase('Work')
  await parallel(plan.batches.map(b => () =>
    agent(`work task lines ${b.tasks} as a ${b.session_type} session`, {
      agentType: 'flywheel-construction-session',
      isolation: 'worktree',
    })))

  phase('Merge')
  await agent(`wt merge --no-remove -C <worktree> for each finished branch`)
}
