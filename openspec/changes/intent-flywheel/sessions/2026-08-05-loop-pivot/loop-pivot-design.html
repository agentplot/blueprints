The flywheel: intents, bolts, and the phase gate between them

OpenSpec is the foundation of both loops, as three schemas in one hierarchy: intents (design, on blueprints main) burn fog into decisions and book writebacks; at the operator's phase gate a settled slice is handed to a bolt (construction tracking, also on main), whose conductor drives spec-driven changes across bolt branches in the built repos. Sole-writer conductors own each change; everyone else requests via herdr prompt or the change's inbox/.

The whole system on one page

The books and context map are the shared state both loops read. The outer loop is the only writer of design; the inner loop is the only writer of code. The phase gate is the one hand-off: design lives here; bolts track construction from here while the code lands in the built repos.

Outer loop — intent changes on blueprints main

One intent = one OpenSpec change on blueprints main, under a custom intent schema. Wayfinder's discipline survives — the unit of work is a decision, the map's settled / candidate / open statuses are the fog gauge — but the tracking is OpenSpec's: tasks.md is the frontier, checked off as work lands, growing as new decisions surface. That back-and-forth in the artifact sequence is what makes OpenSpec fit fog: progress is incremental in both directions, and archival is built in — closing an intent archives its whole record as one unit.

The intent change — everything the intent produces, in one folder

Every kind of outer-loop work is a task in tasks.md

task typeproduces
researchan answer, recorded in the relevant decision record
design sessiona lavish report under design/; closed decisions under decisions/
prototypeproof in the spike repo; findings under prototypes/

writeback — mapnode statuses moved; map-check --write green

Decisions are artifacts, not tasks: a task closes a decision, and a closed decision often appends new tasks — writebacks, ADRs, handoffs, or fresh questions. The split: decisions/ records are intent-scoped and live here; an ADR is the repo-scoped consequence, written where the code lives so the built repo's own history explains itself.

The phase gate — design hands off to a bolt

Nothing enters construction on its own: the phase gate is the operator's word, given directly to the intent conductor. On release, the conductor requests the bolt — creating the flywheel-bolt change and auto-starting bolt-<slug> when none exists, prompting the running one otherwise — and never writes the bolt change itself. Batching related handoffs into one bolt is the normal move, and more work can be pushed into a live bolt at any time.

Small, well-defined intent

Short-circuits. Its change is born with handoff tasks only — no design sessions, no decision records. A record that costs more than the decision it captures is waste.

Foggy intent

Hands off task by task: a settled slice's handoff task can be released while the rest of tasks.md stays in fog. Waiting for a whole intent to finish means waiting forever; looping on it forever means vibing the prototype into the product. Prototypes prove decisions and die — the released slice is rebuilt from its generated proposal in the built repo.

Intent that grew

Decomposes into child intent changes. Intents never compose upward — composition is what the map is for.

Monitoring — OpenSpec UI, no custom dashboard

The openspecui board on blueprints@main already shows intents and bolts as changes with task progress — the phase gate needs the operator's word, not a page. Releases are told to the conductor directly. Deferred gap, revisited only if felt in use: a cross-intent release queue with ripple prediction.

From release to construction — what a release actually does

1 · Proposals generated + reviewed

The conductor delegates an agent per released handoff task to generate the OpenSpec proposal in its built repo, then runs the batch spec review across all of them — cross-repo alignment while it is still cheap.

2 · A bolt owns them

The release names its target. New bolt: the intent conductor creates the flywheel-bolt change and its conductor auto-starts — a long-lived herdr session on blueprints main, the super-conduct successor, which cuts a bolt branch per involved repo and owns dispatch, merge-backs, batched acceptance, and landing. Running bolt: one herdr prompt (or an inbox/ file) and the proposals join its registry.

3 · Completion flows back

Landing a proposal checks off its handoff task in the intent's tasks.md; findings that alter the design append new tasks. The conductor archives the intent when its tasks empty and writebacks are green.

Managing the intent sessions works the same way from the other direction: the design conductor starts and continues per-intent sessions through herdr. A second control surface is worth proving in the spike — the schema's custom instructions could make OpenSpec UI's kanban itself a trigger, so "continue" on an intent card starts the herdr session for it.

Bolt conductors run in the blueprints repo. A bolt can span built repos, so its conductor sits where the cross-repo view lives — the map, the intents, its own change — and reaches out: bolt branches and worktrees in every affected repo (herdr works from anywhere via --cwd), cross-repo sequencing in one place, merges serialized per repo. The bolt stays alive between batches, waiting on the operator and accepting pushed work at any time.

Ripple work — generated, never authored

"Update the atlas SDK → update the dev portal"; "change a framework → its dependents need updating." The dependency knowledge already exists as data: context-map edges and kit version pins. Ripple work is generated at build time, on demand: when a released change lands in a framework, the conductor queries the map for dependents and appends the ripple handoff tasks then — or, mid-build, a blocked change gets its sibling-repo proposal generated the moment the need appears (cortex blocks, spins up the gvc feature, resumes). No up-front waterfall of the whole cross-repo graph; the intent conductor names the predicted ripple (map edges out of a staged handoff) when it presents the release, so the operator sees the blast radius before giving the word.

The books drop their proposals.md chapters. Chapters describe the destination; the build list lives in the intents' handoff tasks, and the generated proposal in each built repo cites the chapters directly. This is a books-convention change that rides along with this design — books/CLAUDE.md retires the proposals-chapter requirement (verification chapters stay).

Inner loop — super-conduct's structure, industry vocabulary, tests at their natural times

Keep the orchestrator, the issue-graph backlog, delegated work branches, and batched deep testing. Drop the invented vocabulary and the fixed "bar" scheme: test suites are pipeline stages (continuous-delivery style), each run at the point in the merge topology where it pays for itself. Moon makes the stages repo-neutral — the skill says "run the commit stage", moon resolves what that means in this repo.

The e2e stall that bogged super-conduct down is solved structurally: acceptance suites never run inside a work branch — a branch that believes it needs broader proof escalates instead of upgrading its own stage.

The reorg reshapes this table: once projects break out into smaller repos, within-repo affected detection matters less and the acceptance stage increasingly means cross-repo integration — a kit change proven against the products that pin it, at pinned versions. The stage names stay; what each stage exercises shifts with repo size.

A map of alternatives, not a prescription

The skill stops dictating step-by-step and instead states the decision points with criteria, letting the agent choose and record the choice in the issue:

Branch shape

Bolt branch + nested construction worktrees for a multi-proposal bolt; a single work branch straight off main for a lone small change. Criterion: how many changes share unfinished contracts.

Working arrangement

Solo / reviewed / paired per change. Criterion: cost of a plausible-but-wrong success claim vs the latency of review round-trips.

Batch size

Acceptance batches of 2–3 merges by default; batch of one when a change is high-risk. Criterion: blast radius of a red acceptance run across unmerged siblings.

The foundations contract — what makes a repo orchestratable

This is the fix for super-conduct's repo-boundness. The skills never name a repo's commands; they name capabilities, and each repo satisfies them with standard tooling. Readiness becomes an audit, not a vibe — and the audit itself can be a skill.

worktrunk

  • .config/wt.toml gates per pipeline stage, calling moon
  • branch-derived ports/resources so parallel worktrees never collide

moon

  • shared task names: lint · test-unit · test-integration · test-e2e
  • affected detection (moon ci) + caching — the commit stage stays fast for free

OpenSpec — the foundation

  • intent schema on blueprints main drives the outer loop; archival built in
  • generated proposals in every built repo drive construction, citing the chapters + intent they derive from

GitHub issues — conversation only

  • cross-repo mentions, notifications, team discussion
  • never the tracking database — that is OpenSpec's job

herdr

  • worktree + agent lifecycle, panes, monitoring
  • explicit worktree paths until the bare-layout naming fix lands

Repo self-description

  • CLAUDE.md names the reset/bootstrap path and review surfaces
  • none of the kit repos run moon today — adoption joins the reorg roadmap

Where this lives — the flywheel plugin

The loops are designed as chapters of books/aidlc-design (the process book already frames inception → construction → operation, and its "Conducting" chapter is the seed of the outer loop). They distill into the flywheel plugin with two skills that keep the marketplace's word+phase convention: flywheel-inception (the design loop) and flywheel-construction (the build loop, repo-readiness audit folded in). One plugin because the phase gate is exactly the point where the two skills must agree. Prototype as project skills here, move to willdan-marketplace once stable, iterate without publishing via a local marketplace (/plugin marketplace add <path-to-working-tree>).
