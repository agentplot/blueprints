Decision 1 · channels

When does each human-in-the-loop channel apply?

Discord is the async unblock channel — the inner loop churns, an agent hits a question worth one sentence, you answer from wherever you are; intake asks its routing questions the same way. Lavish and plannotator are the desk channels, where a design session and you work a surface together. An exchange started in one hands off to the other contextually. What is undecided is where each boundary actually falls.

The three candidate boundaries

recommendedBy the shape of the answer
The channel follows what you have to produce, not where you are. A sentence with nothing to read first is Discord. Notes in the margin of a document that already exists is plannotator. Choices across coupled decisions, or anything needing options side by side, is lavish. Cost: an agent has to judge the shape before it asks. In practice the judgment is easy — "can I say the answer in one line without opening anything" is a question the agent can answer about its own question.
By where you are
At the desk → surfaces. Away → Discord. Cost: makes the channel a function of something no agent can know, so it degrades into asking you which channel you want — and it produces walls of Discord text whenever you are out, because the fallback has no size limit.
By which actor is asking
Intake and inner-loop agents → Discord. Design sessions → lavish. Conductors → plannotator. Cost: clean to state and wrong in the common case — a design session that hits a one-sentence blocker while you are out has no way to ask, and a bolt's review of a written proposal genuinely is a plannotator round.

Recommendation — shape decides the channel; a second rule decides who waits.

Discord is non-blocking: the agent asks and keeps working on anything the answer does not gate. The two desk channels are blocking rounds: the session stands at the surface until you have been through it. That second axis is what makes the boundary usable — if an agent would have to stop and wait anyway, the question was never a Discord question.

Handoff is escalation only. Take the cheapest channel that can carry the answer; when it turns out it cannot, say so and open the surface, leaving a pointer in the Discord thread. Never the other direction — a surface question does not get re-asked as a one-liner.

Sub-question 1a — bridge triggering

This one turned out to be documented rather than unknown. From the Discord plugin's own ACCESS.md (~/.claude/plugins/cache/claude-plugins-official/discord/1.0.0/ACCESS.md):

  • DMs from an allowlisted sender trigger the session on every message. No mention needed.
  • Guild channels are opt-in per channel and default to requireMention: true — an @bot mention, a reply to the bot, or a match against a configured mentionPatterns regex. /discord:access group add <id> --no-mention makes it fire on every message in that channel.
  • So "can it trigger on any message" is a config choice, not a limit. The real question underneath is which session is bridged — the plugin binds one Claude Code session per bot token, so two bridged sessions on one token both receive every message.
recommendedOne bridged pane: intake
DM policy allowlist, no guild channels. Intake is the singleton that is always up, so it is the standing thread. It answers its own routing questions and relays anything else with herdr agent prompt or the change's inbox/ — the two paths that already exist. Cost: one hop between the asking agent and you. Intake becomes a relay as well as a router.
Every conductor bridged
A bot token and DISCORD_STATE_DIR per actor; one DM thread per conductor. Cost: N Discord applications to provision and N threads to watch, and you have to know which thread is which actor before you can read the question.
A guild channel per actor
One server, #intent-flywheel, #bolt-rocs-records, and so on. Cost: does not work with one bot — every bridged session on that token receives every channel's traffic. It only becomes viable with per-actor tokens, at which point it costs what the middle option costs plus a server to keep tidy.

Sub-question 1b — a webhook receiver for remote intake

Recommendation: no, and say why in the book.

A DM to the bot already is remote intake — it lands in the intake pane as a channel event with the sender checked against the allowlist. A webhook receiver adds a listener to run, an auth surface to get right, and a second delivery path for the same job. It earns its keep only when a non-Discord source needs to file intents (a form, a GitHub issue, email), and nothing has asked for that. Revisit if it is felt.

Decision 2 · launch points

Where are plannotator and lavish opened from, and by whom?

Much of this is deterministic and only needs writing down: plannotator at review moments on written artifacts, lavish when a design session builds an interactive surface. What is genuinely open is whether plannotator can be a launch point in the other direction — does its feedback path, delivered to the conductor that ran annotate, reach far enough to spawn a design session against the intent?

Grown since you first opened this page: three more open sub-questions from your review of the schema's sessions instruction — 2a the launch pointer, 2b the criterion and profile count, 2c presentation coaching. They are below the main recommendation, and carry options but no recommendation.

The deterministic half — the part that just needs stating

MomentSurfaceWho opens it
Intake has written intent.md and the operator is deciding whether to work itplannotatorintake (it wrote the file)
A conductor has revised a canonical artifact after draining an inbox requestplannotatorthe intent conductor
A session has a decision draft in its own directoryplannotatorthe design session
A session's batch has coupled decisions, options to compare, or a diagram to worklavishthe design session
A bolt's generated proposal.md is up for human reviewplannotatorthe bolt conductor

One rule generates that whole table: the file's sole writer runs the review on it. That is not a new rule — it is the sole-writer decision applied to review, and it removes the only ambiguous case (who annotates a session's decision draft: the session, because the draft lives in its directory).

The open half — can plannotator start a design session?

What the tool actually does: plannotator annotate <file> is a blocking command that returns your annotations to the session that ran it — --json, --gate, --result-file are all shapes of that same return. Feedback reaches exactly one place: the invoker. There is no fan-out and no addressing.

recommendedYes — through the conductor, which is the only mechanism there is
plannotator hands the annotations back to the conductor, which triages each one into exactly one of three: a correction it applies and re-walks forward; a decision your annotation closed on its own; or work that needs design, which becomes an appended Design task and then a session with a directory and a batch. So plannotator is a launch point, the same way the board is one — it produces the task; the conductor spawns the session. Cost: none structurally; it is one more triage rule in the conductor's turn. It does mean a review round can end with "I opened a session for this" rather than a revised file, which should be said out loud when it happens.
No — annotations only correct the artifact under review
A review round is bounded: fix the file or reject it, nothing else. Cost: your most natural review moment loses the ability to create design work, so a real question either gets crammed into the artifact as prose or gets dropped. This intent's own design-catalog decision came out of a plannotator round; under this option that round could not have produced it.
plannotator spawns the session directly
Wire a gate or hook so an annotation tagged as design starts a session. Cost: breaks the sole-writer rule — a session would exist without a conductor having assigned it a directory, a batch, or a place in the intent. Also nothing to build it on: feedback goes to the invoker, so the "spawn" would still be code running inside the conductor.

Corollary worth writing down: plannotator output is never handed to another actor. No --result-file pointed into someone else's directory, no relaying raw annotations. The invoker owns the feedback and turns it into requests through the two paths that already exist.

Three more, from your review of the schema's sessions instruction

The schema's sessions instruction says what a session directory is called, who names it, what happens on collision, and how output is promoted. It says nothing about how a session comes to exist — the conductor launching it under the flywheel-design-session profile, per the inception skill. An opsx-only session therefore learns the conventions but not the launch.

Decision 3 · the books

What replaces the books' proposals.md chapter?

books/CLAUDE.md still requires one per system book as the bridge from chapters to openspec/changes/, and the book skills are built around it. The flywheel gives that role to intents' handoff tasks and bolts' registries, so the chapter and the skills that feed on it both need somewhere else to point.

What is actually attached to that chapter

ConsumerWhat it does with proposals.md
book-suite-scaffold, book-add-systemCreate the chapter in every new system book.
book-chapter-readyLints the five-field entry shape and checks each Verifications gate: row names a real catalog id in verifications.md.

The options

recommendedRetire the chapter; the loops hold the build list
An intent's Handoff tasks are what is ready to build; a bolt's proposals.md registry is what is being built. book-decompose survives, retargeted: given a book and a chapter it produces a handoff task line plus the proposal skeleton the bolt will use, still reading verifications.md and contracts.md to fill the docking. openspec-construction's propose skill reads the bolt registry instead of a book chapter. The scaffolding skills stop creating the chapter; the proposals lints in book-chapter-ready and the unmineable-proposal finding retire with it. Cost: a book alone no longer shows what is left to build. That list was already the thing most likely to be stale — the book is the destination record and the frontier is in openspec/, which is the flywheel's premise. It also ends a name collision: a bolt's registry and a book chapter were both proposals.md.
Keep it, redefined as candidates
The chapter stops being commitments and becomes an inventory of units the design implies; intents mine from it. Cost: two lists that have to agree, and no one is the sole writer of the book one. Every book carries a chapter that drifts from the intent tracking it, and the drift is invisible until someone builds from the wrong list.
Keep it only outside the flywheel
Books whose systems are tracked by an intent drop it; the rest keep it. Cost: a convention with a condition, so every author has to know which books are which before they can read books/CLAUDE.md — and the set changes as intents open and close.

The one thing that must survive the retirement: verification docking.

A proposals entry's Verifications gate: row is the only content the chapter carried that nothing else holds — the declaration of which fixtures a unit reuses, which it adds, and which harnesses it extends. Recommendation: that declaration moves onto the bolt's proposal, where it is actionable, with book-decompose still reading verifications.md to fill it in. The verification chapter itself is untouched; only the list that pointed at it moves.

Decision 4 · the chapter set

How do system-design-inception.md and openspec-construction.md fold into the loop chapters?

Absorbed outright, or kept as dependencies the loops invoke? This is the decision the chapter rewrites are blocked on — two writeback tasks name it as their blocker.

The two chapters hold two different kinds of content, and that is what resolves the question. Practice — what mining a chapter into a unit is, what OpenSpec's artifact sequence is, how a wave of units moves. Decision 5 · the phase gate

May a lone generated proposal skip the bolt?

Is "a lone generated proposal skips the bolt and runs one reviewed work branch off main" the written default for small changes, or does every released handoff go through a bolt?

What a bolt costs: a change directory on blueprints main with bolt.md, a proposals.md registry and tasks.md; a long-lived conductor pane; a bolt branch in the built repo; a serial merge tail. What it buys: sequencing across more than one proposal, a registry of what landed, one archive unit, and a row on the board the intent can point at.

recommendedShort circuit, on a mechanical test
A released handoff skips the bolt when all three hold: one built repo, one proposal, nothing else staged depends on it. Any one failing means a bolt. The rationale is what a bolt is for — it exists to sequence and track more than one proposal across a slice, so a bolt with a one-row registry is a directory that adds a hop. The handoff task line records the built repo's change id where it would have recorded a bolt id. Cost: two paths to describe instead of one, and a test to apply at the gate. The test is mechanical, so it is a check, not a judgment call.
Every handoff goes through a bolt
One motion, no branching in the practice; every released slice appears on the board as a bolt. Cost: a one-file doc fix carries a change directory, a registry with one row, and a long-lived pane. It also contradicts intake's third route, which already says some work gets no tracking at all.
You decide at each gate
The short circuit exists but is named per handoff, not by rule. Cost: every release becomes two questions instead of one, and the answer is nearly always predictable from the three facts above — which is an argument for writing the test down rather than re-deciding it.

Two follow-ons the recommendation needs an answer on:

Who runs a short-circuited change? The sole-writer rule holds either way — the intent conductor requests, never writes. The lighter reading is that it starts a plain session in the built repo (/opsx:ff and the normal PR), rather than a named bolt- conductor, and records the change id on the handoff task line. The built repo's PR is the trail.

What if it grows? If a short-circuited change turns out to want a second proposal mid-flight, recommendation is that it finishes as it is and the second proposal becomes a new handoff task — which then fails the one-proposal test and gets a bolt. Cheaper than migrating a change into a bolt halfway through.

  • .claude/skills/flywheel-inception/SKILL.md — the handoff-is-a-request paragraph gains the short-circuit branch.
  • books/aidlc-design/src/conducting.md and spec-driven-construction.md — the phase gate described with both exits.
  • flywheel/E2E.md §4 — the walkthrough takes the bolt path; the short circuit is named as the other exit.
