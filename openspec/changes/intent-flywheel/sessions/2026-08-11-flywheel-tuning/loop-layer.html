The loop layer — design center

The flywheel's loop layer as settled by the 2026-08-11 tuning round: durable prose in git, mutable state on the org's tracker, approvals as board gestures, sessions as vanilla agents. Successor to the 2026-08-07 page, which stands as the trail.

Why

What this layer is for

the model before the mechanism

A few developers, a fleet of agents, and ideas arriving faster than they can be built. The loop layer turns that stream into shipped code: every fragment is triaged the day it arrives, uncertainty is burned into records before anything is built on top of it, and the operator's attention is spent as a handful of board gestures instead of continuously. The tuning round's diagnosis: most of the previous ceremony existed to make shared markdown files safe to edit concurrently. The tracker dissolved that root cause.

Three commitments everything else derives from these

1 · Durable prose in git; mutable state on the tracker. Records — the intent, decisions, questions, assertions, session reports — are files, written once and reviewed. Work items, their states, the queue, dependencies, and the narrative are GitHub Issues: changed by one API call, no worktree, no collision. Nothing is recorded in both places; a file keeps only terminal facts.
2 · The inner loop never writes the outer. Design (intents) and construction (bolts) corrupt each other when interleaved. A construction finding travels back as a queued item on the intent's milestone — never as an edit to a design record. The open item is the obligation; nothing needs a second ledger to avoid being lost.
3 · Attention is batched, as board gestures. One batch moved to Ready per approval, never one approval per item. One annotation round per page. Assignment reads in three native gestures: assignee = whose word, Team = whose machine, Ready = go — all on one board, all doable from a phone.

The system, as one conveyor

Raw input enters at dispatch, which triages it into tracker items and nothing else. The design loop converts uncertainty into decisions and accretes direction as assertions — and the assertion IS the proposal: written when work is identified, released as itself, specced from directly, never restated. The conductor composes what is ready into a Backlog batch — a unit for construction, an elaboration for design; the operator moves it to Ready; a bolt drives it to main. Findings flow back as queued items. The books and the map receive the destination from the design loop only.

The item lifecycle one ladder for every item

state:queuedoperator's word, or the batch's Ready move→ state:readya session starts on it→ state:in-progressevidence lands→ closed:done

Exits at any rung: closed:declined · closed:superseded · closed:parked (waiting on an external event, reopenable — parking finally has a state). Anyone queues; an item born of the operator's own word is born ready — approval derives from origin, not from a second gesture.

Sessions are vanilla agents. A work order is four things: the change id, the type, the item numbers, and a sentence or two of goal — worktree, directory and model are launch mechanics. Enforce with mechanisms, delete the prose rules they make redundant: the merge gate catches broken books, worktree isolation contains edits, tracker attribution names every writer. Discoveries are queued items, filed in a minute; escalation is for being blocked; the andon cord is for a contradiction no further work inside the batch can fix.
Personas are org-owned lenses, not actors. .claude/agents/user-*.md live with the org (blueprints today; each built repo grows its own user types) — a stand-in for someone who uses the built thing, run under proposal-review and code-review. The plugin ships none.

Flows

Every entity, every path, every dead end

the dead ends are where things rot silently

Each entity walked birth to end. Legend: operator dispatch intent conductor bolt conductor session reconciler — amber states are where a human appears; green states are terminal.

2 · Question questions/<slug>.md + its item, both at birth

Born from a session discovery, a bolt finding, a round, or the operator. Four doors out, three dead ends.

Dead ends: closed:superseded (scope moved) · absorbed into a sibling (comment says which) · closed:parked (external event; reopenable). A question never closes without its decision record.

3 · Decision decisions/<slug>.md — terminal in git

Born when a question closes, wherever the word was given. Its consequences fan out as queued items: writeback items (type:writeback on the intent milestone) · new assertions · new questions · or nothing, the record being the whole outcome. One answer per record; authoritative on its decision, provisional on its measurements.

4 · Assertion — the proposal assertions/<slug>.md + its item

written + queuedblockers close, no parent batch→ settled + unboltedhandoff item names it; operator moves the unit→ Readyhandoff session moves it to bolt/<slug>→ spec → build → reviewlands through the gate→ closed:done + ref

The record is written the moment work is identified; the spec derives from it and the decisions it cites, read fresh from disk — nothing restates it. Progress is the item's comment history; the landing SHA is the closing comment, and the terminal ref is appended to the record. Dead ends: superseded before release · split into narrower assertions · declined by the bolt (back to the intent, queued). An unmineable assertion goes back to the intent to fix — the proposal-writing exception drafts the split only when the work order says the split is the bolt's.

5 · Batch unit or elaboration — the approval, and the gate itself

composedflywheel-batch: sub-issues + board→ Backlogthe operator's move→ Readyconductor relabels sub-issues ready→ workedall sub-issues closed→ closed

conductor composes at the queue — grouped by thread, not by type: a prototype, the questions it answers, and the writeback of its findings are one approval; operator moves; reconciler makes sure the move is seen. The release covers every session inside the batch — the conductor partitions the sub-issues into typed sessions at work time. A released handoff item drafts the bolt plan on the standard template and runs it past the operator in one plannotator round before custody moves. Writeback elaborations release as scheduling — no permission existed to need. A batch pulled back to Backlog before work starts is a retraction; nothing else demotes.

6 · Session a vanilla agent with a goal

work order4 fields, 2 sentences→ workingitems commented, files committed→ reportconductor merges + closes items→ torn down

A session that edits files gets a worktree and its branch merges through the full gate; a session that only reads gets none — no branch, no merge, no teardown. Batch generously, partition by judgment: type is the hard boundary (a session loads one type skill); within a type, related topics share a session, unrelated ones split, prototypes ride alone. Exits: the andon cord (the batch builds on a disproved claim — stop, hold, report) · a blocked escalation to its conductor. Never: waiting on the operator mid-batch.

7 · Bolt born only past the gate

handoff moves ready items inreconciler starts bolt-<slug>→ scaffoldedopsx:new, member = depth→ workedmerge criteria hold→ landedoperator closes the milestone→ archive job → archived

One bolt branch + worktree per involved built repo, alive for the bolt's life; construction on nested worktrees off them; batched acceptance on the bolt branch; each repo lands through the full release gate, one writer to main at a time. The release that created the bolt covers every wave inside it. For work too small to warrant a spec-driven change in the built repo, the build session starts in --permission-mode plan — every edit mechanically blocked until the conductor approves the plan against the item's claim — with bolt-no-spec a per-batch work-order choice, deliberately not a schema. Fold-time cleanup is mechanical (panes, worktrees, branches go as they finish); the conductor is stopped when its milestone has no job, and closing the milestone on GitHub is the archive signal — the reconciler charges a fresh session to openspec archive.

8 · Escalation — HIL from the inner loop the tracker carries the record, dispatch carries the DM

session blockedherdr prompt to its conductor→ needs-operatorcomment + label on the item→ DM'ddispatch → the item's assignee→ answeredcomment; reconciler nudges the waiter→ resumed

One line of question, the options if any, a pointer to evidence — never a report. Dispatch is the accelerator, not a dependency: the question sits visibly on the board with a GitHub @mention as the native fallback, so a dead dispatch delays nothing the assignee can see and answer directly. A withdrawn escalation (the agent found the answer) closes with a comment saying so. The outer loop never enters this machine — intent conductors reach the operator directly on the desk channels.

The operator's word is applied directly, wherever it lands. A meeting outcome, a correction, an instruction — whoever holds it edits the record or item it names, comments the change, and the conductor sees it on the next query or nudge. Items born of the word are born ready. No drain cycle, no relay ceremony, no approval of your own words.
Escalation runs one way. Take the cheapest channel that can carry the answer; never demote a question back down or re-ask it on a cheaper one. The outer loop is high-touch: intent conductors and their sessions reach the operator directly — dispatch relays only the inner loop's questions to a possibly-absent operator.
Hosts & owners

Scaling past one machine — and one person

assignee = whose word · Team = whose machine · Ready = go

Ownership is the assignee

The developer whose word settles a change is its items' assignee — set by dispatch at triage, inherited by batches at composition, resolved by escalations for their DM target. One native field, on every board view, nothing in git to go stale. Intents scale by designer, bolts by builder; today one developer holds every assignment, and the design treats that as the N=1 case with zero added ceremony.

Placement is the Team field

Each host's reconciler starts conductors only for work whose board Team matches its own host name; unclaimed work falls to the default host. Placement becomes an operator gesture on the board — the same family as the Ready move — instead of a hand-edited actor row.

flywheel reconcile subsumes flywheel up: every pass converges the manifest's standing rows first, then the tracker-driven conductors. Each pass is a pure function of manifest + tracker + roster — run it by hand, on --interval, or from a webhook later; --dry-run prints the plan and touches nothing. fleet.yaml carries the standing rows plus placement: tracker:, conductors_cwd:, a teams: map from Team-field values to hosts. Cross-agent messaging survives only where it is in-flight — herdr prompts for work orders and reports, same host, ephemeral; everything durable is items and comments.

Credentials the app, the key, the split

The app is org-owned and tracker-only. One GitHub App per org (willdan-flywheel; agentplot-flywheel is the sandbox) with Issues and org Projects read/write, nothing else. Machinery writes run as the app's bot identity — cleanly separated from human writes in every audit trail. Setup is ten minutes of IT time; flywheel-setup converges labels, the Project and its fields idempotently.
The key follows the fleet host, never the developers. Only the machinery mints tokens, and the machinery runs where the fleet runs — one workstation today, the central server when it moves. Developers' own gestures ride their own GitHub logins, which is the attribution an approval needs. A second host before the server: a shared 1Password vault, rotated on GitHub's two concurrent keys. A checkout-free dispatch plus a tracker-driven reconciler is what makes the server destination clean.

The bin tools the plugin's bin/, on PATH when installed

tooldoes
flywheel-tokenmints and caches the app's installation token — key from ~/.config/flywheel/env, a path, or op:<vault>/<item>; a warm cache needs no key. GH_TOKEN=$(flywheel-token) gh … is the one credential path for machinery writes.
flywheel-setupconverges labels, the org Project (copied from the hand-built "Flywheel Template" with its Board/Roadmap/Triage views when one exists), Team/Quarter/Start/Target fields, and the Backlog/Ready status options. Run once per org, safe always. Org-level customization is deliberately out of scope.
flywheel-batchcomposes a Backlog batch (--kind unit|elaboration) from queued items in one call: parent issue, sub-issues, milestone (created, due today unless --due), the board, Status Backlog, Start/Target defaulted to today (--start/--target with a reason when bigger). Refuses items already batched. Never moves anything to Ready.
flywheel-migratemoves a change's unchecked tasks.md lines onto the tracker mid-flight: items typed from sections, RELEASED handoffs born ready, blockers quoted for wiring, one milestone per change. Deleting the migrated file is the operator's commit.
flywheel up / status / reconcilethe fleet layer: up starts running-state manifest rows into the org's herdr session, verifying the first prompt actually submitted; reconcile runs that pass plus the tracker-driven conductors and nudges, one-shot or on --interval, with --dry-run printing the plan.

Schemas are v2 and validate. The apply instruction works the ready set to empty, composes batches at the queue, and stops — an empty ready set with a full queue is the correct resting state. Do not install the v2 user schemas for an org until its tracker exists and its live changes are migrated.
